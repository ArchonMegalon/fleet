# Whole Project Missed Scope Acceptance

Last updated: 2026-06-20

This file records additional whole-project goals that must stay in the active gold scope. It is deliberately user-facing and tester-facing: a proof artifact can pass while the product still fails if a normal user sees confusing copy, broken contrast, clipped installer text, or unclear workflows.

## Definition Of All

For Chummer, "all" means every path a normal player, GM, returning Chummer5A user, tester, or site visitor can touch:

- public website routes, downloads, help, status, and account claim flow;
- Windows and Linux installers, updater handoff, package metadata, and first launch;
- desktop shell, menus, dialogs, overlays, every add/edit/select workflow, and OS light/dark themes;
- SR4, SR5, SR6 character creation, import, save/load, rules explanations, and legality warnings;
- Alice, Origin Dossier, Instant Help, and every optional assistant/provider surface;
- design docs, release docs, proof artifacts, E2E receipts, and human-facing generated docs;
- provider inventory and external lanes that can affect public copy, help, video, analytics, or generated assets.

## Additional Goals

### 0. Always Ask What We Missed

Acceptance:

- Every whole-product pass must end by asking what a normal player, GM, returning Chummer5A user, first-time site visitor, installer tester, Linux user, maintainer, and release auditor would still reject.
- "What did I miss given the whole project as scope?" is itself a standing additional goal: newly discovered misses must be added to this acceptance file, converted into a tracked code/test task, or explicitly marked out of scope with a review trigger.
- Relevant misses become either a code fix, a failing test, an acceptance-gate bullet in this file, or a documented out-of-scope decision with owner and review trigger.
- Stale audit findings are not copied forward as truth; each must be reclassified as fixed, still relevant, superseded, or unproven from current repo and live surface evidence.
- "Gold" cannot be claimed from proof artifacts alone when tester-visible copy, contrast, clipped text, broken flow labels, missing platform package paths, or unclear user choices remain.
- The missed-scope review is a separate goal from fixing the currently visible bug: it must actively look for adjacent failures, duplicated bad patterns, stale vocabulary, and hidden platform variants before the pass is considered done.
- A fix that changes one surface must ask whether the same component, copy pattern, color token, package assumption, or workflow label exists anywhere else.

Review lenses:

- first-time visitor: can I understand and download without reading internal process language?
- skeptical non-AI user: does this look like human-designed software rather than an AI/proof showcase?
- returning Chummer5A user: can I find familiar character-building actions without relearning internal names?
- mouse-only tester: can I complete core SR4/SR5/SR6 flows without keyboard escapes or hidden navigation?
- Linux tester: can I install, update, claim, and diagnose without Windows-only assumptions?
- release auditor: can I reproduce the release truth from checked-in scripts, docs, and current public pages?
- maintainer: can I tell which provider lanes are draft-only, verified, disabled, or out of scope?

### 1. Human First Public Surface

Acceptance:

- Unauthenticated `chummer.run` must read like a minimal human-designed product site, not a proof console or AI showcase.
- Hide Black Ledger from the main homepage until its visual and behavior bar is clearly ready.
- First-visit navigation must stay as small as the page itself: Home, download, help, status/support links only. Maintenance, roadmap/changelog, feedback loops, Black Ledger, proof, receipt, provider, and horizon language must not leak into the normal public header, drawer, or minimal footer.
- No visible "generated by AI", "AI-generated", "provider", "operator lane", "proof receipt", "receipt", or internal release machinery on normal public routes.
- The live public copy gate has a stricter first-visit route tier for `/`, `/downloads`, `/status`, `/help`, `/faq`, `/what-is-chummer`, and login/claim entry. Those routes must not mention AI/Alice, Black Ledger, Origin Dossier, proof, receipt, operator, provider, governed, artifact, registry, horizon, or generated workflow language.
- Public homepage answers three questions in seconds: what Chummer is, where to download it, and how to get help.
- NeuronWriter/ClickRank optimization must not add clutter or AI-forward copy.

### 2. Desktop Contrast And Readability

Acceptance:

- Every desktop surface must pass light and dark OS theme visual checks with no white-on-white, black-on-black, hidden values, or overlapping placeholder/value text.
- ComboBox, TextBox, NumericUpDown, tabs, grids, context menus, overlays, About, Help, Devices and Access, Origin Dossier, SR4 metatype, Add Quality, Add Skill, Add Gear, and report issue all require coverage.
- Source-level theme tests are not enough by themselves; at least representative screenshot or pixel evidence must exist for installed builds.
- New Avalonia desktop ComboBox/TextBox constructions must explicitly apply the shared shell theme helper or fail test review.

### 3. Installer And Update Trust

Acceptance:

- Windows installer text must be compact, readable, and not clipped at default DPI and common scaled DPI.
- Whole-product gold requires native Windows visual evidence for the promoted installer; a Linux incompatible-host startup skip may satisfy registry portability, but it must not satisfy visual/DPI installer polish.
- Linux updater must not depend on `gio open` for `.deb` installation; it needs a native install path or a visible fallback.
- Linux install-link must show a copyable URL if browser dispatch fails.
- Arch/CachyOS support requires an AUR-compatible path with `makepkg -si` proof or an explicitly documented unsupported state.
- Downloads publish only once per day at 08:00 Europe/Vienna unless an explicit forced publish is requested.
- Builds happen only when needed, and only for the platform needed for that proof, except scheduled public Windows+Linux releases.

### 4. Claim Your Copy Flow

Acceptance:

- The account flow should say "Claim your copy" rather than "login via webpage" where the user's intent is linking a downloaded install.
- Windows and Linux public installer buttons must download the current file directly for guests and signed-in users; account linking is a separate claim/continuity path after the copy exists.
- Manual activation is not part of the normal path.
- Browser/account return pages should say "Claim this copy" or "Claim your copy", not "finish linking", "manual launch", "manual callback", or "login via webpage".
- A signed-in user should get the most comfortable path available: background browser/link handoff where safe, visible fallback where not.
- The optional login video must be available from Help even when already signed in.
- The login/uplink render may personalize with safe account fields, but the product must never leak private data beyond the intended email/name display.

### 5. AI Off Means Hidden

Acceptance:

- The global AI-off preference hides assistant buttons, origin dossier entry points, AI companion/build suggestions, and AI character/companion options where the desktop UI owns the list.
- If AI-off is enabled, normal workflows should not mention Alice, Origin Dossier, local co-processor, or AI-backed support unless the user explicitly opens settings to re-enable them.
- Shadowrun rules data must remain intact; the preference controls product assistant exposure, not source data correctness.

### 6. Origin Dossier Is A Book-First Flow

Acceptance:

- Default flow is simple: select race/metatype and archetype, then build a story.
- Advanced steering controls are collapsed by default.
- The first artifact is the story/book handoff, then FlipLink/PDF, then voice/audiobook, then video.
- Voice selection follows the same comfortable voice-pick workflow already used in Telegram.
- Alice ingests the approved story, not raw steering combo boxes.
- Finished characters can generate dossiers without Alice trying to rebuild the character afterward.

### 7. Rules And Alice Explanations

Acceptance:

- Alice must explain selectable options in the UI, including legality strict vs standard, ware assumptions, build lanes, availability, GM grants, and ruleset-specific consequences.
- If no character is open, Alice selecting a build should create a complete character from scratch using the selected settings rather than throwing an error.
- Rules explanations must be derived from deterministic Chummer outputs and current rule coverage proof, not provider text.

### 8. GM Cockpit And Maintenance Surfaces

Acceptance:

- GM-facing tools must feel like a cockpit, not an internal maintenance list.
- "Horizons" are not a user-facing product category unless the surface is explicitly a maintenance/admin surface.
- Maintenance pages stay behind account/admin paths and use plain labels.

### 9. Instant Help

Acceptance:

- Chummer support should prefer instant answer, optional short video, guided repair, automated check, and issue report.
- Lunacal must not appear in the normal Chummer help flow.
- VidBoard can provide pre-rendered help videos only after provider proof; it is not a live runtime answer source.
- Help must stay minimal: if the workflow needs a paragraph to explain itself, redesign the workflow.

### 10. Provider Inventory And Boundaries

Acceptance:

- Owned tools that affect product quality must be inventoried with bounded roles: Humanizer, Subscribr Tier 7, VidBoard Tier 5, Rybbit, NeuronWriter, ClickRank, Dadan, MagicFit, Unmixr, Heyy, PoppyAI, and related LTDs.
- Provider output may draft, humanize, narrate, render, analyze, or optimize only inside the approved lane.
- Providers do not own rules truth, release truth, entitlement truth, or publication approval.

### 11. E2E Hardness

Acceptance:

- E2E coverage must include first launch, account claim, update check, SR4 BP troll decker with mouse only, SR4 Karma, SR5/SR6 smoke, Add Quality, Add Skill, Add Gear, attributes, report issue, Devices and Access, Help/About, Origin Dossier, Alice no-character build, downloads, and public help.
- Tests must fail on invisible labels, unreadable values, clipped installer text, disabled-looking active controls, duplicate text rendering, non-interactable navigation, and accidental AI/proof copy on public routes.
- "Clean" E2E is not enough if it only clicks happy paths without visual or copy assertions.

### 12. Human Acceptance Backstop

Acceptance:

- This is an additional standing goal for every whole-product pass: ask whether a skeptical human user would call the surface good without reading design notes, release notes, or operator explanations.
- Any user-facing workflow that needs visible explanatory prose to justify its own controls is not finished; simplify the workflow, hide advanced controls, rename the control, or make the next action obvious.
- Public, desktop, installer, help, and account surfaces must use role language a real user recognizes: player, GM, character, campaign, download, claim, update, help, report, restore. Internal words such as horizon, operator, proof, receipt, lane, provider, artifact, governed, parity, or registry are allowed only on maintenance/admin/proof routes.
- Every cross-repo feature must update the same truth chain before it can be called done: design contract, implementation, focused tests, E2E or screenshot proof where visual, public/help copy where user-facing, and release/proof gate where promoted.
- Whole-project audits must classify old findings as fixed, still relevant, superseded, or unproven; repeating stale audit text is not evidence.
- Personalized media, login/uplink renders, Origin Dossier outputs, and support videos may use only explicit safe fields and consented context. Email/name display must be intentional, bounded, and testable; account, entitlement, and private campaign data must not leak into renders.
- AI-off is a trust boundary, not a theme: if disabled, normal user paths must look like a non-AI product rather than a product hiding one button while mentioning assistants elsewhere.
- The current gold blocker list must remain visible inside the working goal until closed: SR5 provider coverage, desktop visual proof, website minimalism, installer DPI polish, Linux/AUR packaging, origin dossier book-first E2E, account claim comfort, and reproducible release proof.
- A release candidate can be technically green and still fail this goal if it feels noisy, generated, clipped, unreadable, overexplained, or internally named.

### 13. Data Safety, Accessibility, And Recovery Are Product Scope

Acceptance:

- Character data safety is part of gold scope: import, save, load, autosave, backup, restore, export, sync/claim, and uninstall/reinstall must have proof paths and user-facing recovery language.
- A crash, failed update, failed claim, failed import, stale rules pack, or invalid character file must leave the user with a clear next action and a diagnostic packet that does not leak private campaign or account data.
- Accessibility is not optional polish: core workflows need mouse-only, keyboard, screen-reader names/help text, focus order, contrast, scaling, and reduced-motion review.
- Localization quality is part of whole-product acceptance, especially German and English first-run, installer, claim, help, error, and settings copy. Literal machine-sounding translations fail the human acceptance backstop.
- Privacy and consent are product features: analytics, personalized renders, support evidence, Origin Dossier media, and AI/provider features must be opt-in or clearly bounded, deletable where applicable, and disabled from normal paths when AI-off is selected.
- Update and package recovery must cover rollback, stale staged files, failed package installation, unsupported platform states, and visible retry instructions.
- Whole-project audits must actively ask what data a user could lose, what path a disabled or non-English user cannot complete, what support evidence would expose too much, and what recovery step is missing before calling the pass done.

### 14. Fit-For-Purpose Code Shape Is Product Scope

Acceptance:

- "Generic" is allowed only for true platform plumbing, fallback rendering, maintenance views, or repeated infrastructure. Player-facing character, rules, installer, support, claim, Alice, and Origin Dossier flows need specialized names, actions, labels, and tests that match the user's job.
- A generic form renderer may not be the promoted user experience when a domain-specific surface exists or is expected by a Chummer5A user.
- Hardcoded strings, routes, release ids, platform lists, provider capabilities, rule counts, theme colors, installer sizes, and publish cadence are allowed only as local constants with a named owner and a test that explains why they should not come from the catalog, registry, design token, feature flag, or release manifest.
- Public/desktop copy must be generated from or checked against the same user-facing vocabulary contract. Hidden compatibility aliases may exist, but they must not become visible labels.
- Code-quality passes must classify each finding as "too generic", "too hardcoded", "correctly specialized", or "correctly centralized" before changing it. This prevents replacing specific domain behavior with broad helpers or spreading one-off constants through the product.

### 15. Reproducible Product Truth Is Product Scope

Acceptance:

- Gold readiness must be reproducible from a clean checkout with checked-in scripts, current docs, current manifests, and current public pages.
- The final gold script, final generated artifact, artifact root, release manifest, downloads page, status page, and publish receipts must agree on the current promoted build and proof root.
- A final artifact that requires a live recrawl under 24 hours old fails when the checked-in artifact is older than that, even if the written verdict says `GOLD_READY`.
- Rules readiness must have current, fetchable SR4/SR5/SR6 coverage proof. A superseded or zero-rulefact proof cannot satisfy whole-product gold.
- Desktop visual proof is part of truth: screenshots or pixel receipts for the promoted build must exist for the surfaces named by the desktop contrast and installer gates.
- Generated or provider-assisted material, including public docs and Origin Dossier story/book output, must pass a humanizer/minimal-copy loop without adding visible "generated by AI" style language. Humanizer improves wording only; it does not own rules, release, entitlement, or character truth.

## Current Concrete Linux Update/Link Gate

The Linux updater and install-link lane must keep the tester-reported WSL/CachyOS failure modes closed:

- `.deb` update apply must use the native package path (`dpkg -i` when running as root, `pkexec dpkg -i` for desktop users) and must not call `gio`, `xdg-open`, or a desktop MIME handler for package installation.
- updater failures must persist a structured `LastFailureReason` and leave pending update state inspectable instead of silently clearing the staged update.
- install-link headless mode must run before Avalonia graphics initialization so WSL/no-GUI users can claim a copy without GL startup.
- install-link browser dispatch failures must print a copyable login URL, print the callback command, persist the browser failure, and keep manual fallback available.
- the installed GUI claim flow may auto-open the browser, but the copyable URL and callback fallback remain the support path when browser dispatch fails.
